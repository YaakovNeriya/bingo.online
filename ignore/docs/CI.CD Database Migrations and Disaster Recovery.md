# תוכנית עבודה: אסטרטגיית פריסה (CI/CD), מיגרציות מסד נתונים והתאוששות מאסון

מסמך זה מתאר את תהליכי העבודה, המדיניות וההגדרות הנדרשות עבור צינור הפריסה (Pipeline) לסביבות Staging ו-Production. התוכנית מתמקדת בניהול סיכונים סביב שינויי סכמה (Migrations), גיבויים, שחזורים והבטחת יציבות המערכת.

## 1. תלות וקשר בין סביבות (Staging -> Production)
סביבת ה-Staging מוגדרת כ"רשת הביטחון" של המערכת, בה נבדקות המיגרציות על נתוני אמת/דמוי-אמת לפני שהן מגיעות ל-Production.
- **הגדרה נדרשת בפייפליין:** חובה לוודא שקובץ `deploy-prod.yml` תלוי באופן מוחלט בהצלחת `deploy-staging.yml`.
- **מימוש טכני:** יש להשתמש ב-`needs: [deploy-staging]` ב-GitHub Actions, או להגדיר טריגר ידני (Manual Approval) לפרודקשן שניתן לאשר רק לאחר שהסטייג'ינג עבר בהצלחה.
- **מטרה:** מניעת מצב בו שני ה-Workflows רצים במקביל על אותו Push, מה שמייתר את תפקידו של ה-Staging כמגן על ה-Production.

## 2. אסטרטגיית גיבויים (Backups)
הגיבויים מתבצעים באופן מותנה, רק כאשר מזוהה צורך במיגרציה (שינוי סכמה), כדי לייעל את התהליך.
- **מדיניות שמירה (Retention Policy):** חובה להגדיר מנגנון ניקוי אוטומטי לגיבויים ישנים ב-Google Drive (למשל, מחיקת גיבויים בני יותר מ-30 יום) כדי למנוע הצטברות אינסופית וצריכת נפח מיותרת.
- **אבטחת מידע:** יש להצפין את קובצי הגיבוי גם בתעבורה (In Transit) וגם במנוחה (At Rest) בדרייב.
- **בקרת גישה:** יש לוודא הרשאות קפדניות (IAM) לתיקיית הגיבויים, כך שרק שירותים מורשים וצוות ה-DevOps יוכלו לגשת לנתוני לקוחות והזמנות.

## 3. סדר פעולות בפריסה (Order of Operations)
קיימת סכנה של התנגשות (Race Condition) בין קוד חדש שעולה לבין מסד נתונים שעדיין לא עבר מיגרציה.
**התהליך הנדרש לפריסה נכונה:**
1. העלאת הקונטיינר החדש (ללא ניתוב טראפיק אליו מה-Load Balancer / Nginx).
2. הרצת פקודת המיגרציה (`docker compose exec backend alembic upgrade head`).
3. המתנה לאישור שהמיגרציה הסתיימה בהצלחה.
4. פתיחת הניתוב (Traffic) לקונטיינר החדש וסגירת הישן.
- **מטרה:** מניעת שגיאות הנגרמות מכך שהקוד החדש מצפה לסכמה חדשה שעוד לא קיימת ב-DB, בזמן שהוא כבר מקבל בקשות ממשתמשים.

## 4. מדיניות Health Checks וטיפול בכישלונות
התגובה לכישלון ב-Health Check משתנה בהתאם לסביבה:
- **בסביבת Staging (בדיקות QA):**
  - **מדיניות:** Halt Pipeline (עצירת הפייפליין).
  - **פעולה:** אם ה-Health Check נכשל, הפייפליין נעצר מיד. הסביבה נשארת "שבורה" בכוונה, כדי לאפשר למפתחים ול-QA לחקור את הבעיה, לבדוק לוגים ולהבין את מקור התקלה.
- **בסביבת Production (סביבת אמת):**
  - **מדיניות:** Automated Rollback (שחזור לאחור אוטומטי) + התראה.
  - **יעד:** צמצום זמן ההשבתה (MTTR) לאפס.
  - **פעולה:** 1. פריסה מדורגת (כגון Blue/Green או Canary). 2. הרצת Health Checks (זמינות, חיבור ל-DB, תקינות API). 3. הצלחה: ניתוב כל המשתמשים לגרסה החדשה. 4. כישלון: המערכת תבצע Rollback אוטומטי ומיידי לגרסה הקודמת והתקינה, תסמן את הפייפליין כ"נכשל" ותשלח התראה דחופה.

## 5. תוכנית שחזור (Restore Plan)
גיבוי אינו מספיק ללא תוכנית שחזור ברורה ומתורגלת. במקרה של כישלון מיגרציה ב-Production, יופעל אחד מהתרחישים:
- **שחזור רך (Soft Rollback):** שימוש ביכולות ה-Downgrade של כלי המיגרציה (`alembic downgrade -1`) כדי לבטל את שינוי הסכמה האחרון, במקביל לחזרת הקוד לגרסתו הקודמת.
- **שחזור קשיח (Hard Restore):** במידה והמיגרציה השחיתה נתונים, יש להפעיל נוהל חירום ששואב את הגיבוי האחרון מה-Drive ומשחזר את מסד הנתונים למצבו טרם הפריסה.
*(הערה: חובה לבצע סימולציית שחזור אחת לרבעון).*

## 6. הקשחת אבטחה בשרתי היעד
- **הרשאות הרצת Docker:** הפקודות בפייפליין אינן צריכות לרוץ עם `sudo` (למשל `sudo docker compose`).
- **פעולה נדרשת:** יש להוסיף את המשתמש של ה-CI/CD (למשל ubuntu/github-actions) לקבוצת `docker` בשרת.
- **מטרה:** הפחתת משטח התקיפה ע"י ביטול הרשאות sudo חופשיות בסקריפטים.

## 📋 רשימת מטלות לביצוע (לפי סדר מדויק)

[ ] 1. עדכון `deploy-prod.yml` שיופעל רק לאחר אישור/הצלחה של `deploy-staging.yml`.
[ ] 2. הגדרת מחיקת גיבויים ישנים (Retention > 30 ימים) בסקריפט הגיבוי ל-Google Drive.
[ ] 3. וידוא הצפנה והרשאות קפדניות לתיקיית הגיבויים.
[ ] 4. הפרדת שלב העלאת הקונטיינר משלב ניתוב התעבורה (Traffic Routing) כדי להבטיח שהמיגרציה מסתיימת קודם.
[ ] 5. **הקמת נתיב Health Check בשרת (`/api/health`)** ולאחר מכן הגדרת Automated Rollback בפייפליין של ה-Production במקרה של כישלון בבדיקה זו.
[ ] 6. כתיבת נוהל שחזור (Restore) ברור וסקריפט חזרה לאחור (`alembic downgrade`).
[ ] 7. הוספת משתמש ה-CI לקבוצת `docker` והסרת פקודות ה-`sudo` מקבצי הפייפליין.
